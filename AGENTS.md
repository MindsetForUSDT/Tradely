## Продукт

Tradeum — русскоязычный SaaS для криптотрейдеров, который после безопасного read-only подключения Bybit должен отвечать на три вопроса:

1. Каков чистый результат после комиссий, funding и корректировок?
2. Какие завершённые позиции сформировали результат?
3. Какой повторяемый фактор в торговом поведении стоит проверить следующим?

Главный пользовательский цикл:

`подключение → асинхронная синхронизация → проверка качества данных → финальные сделки → метрики → разбор решений → повторная синхронизация без потери контекста`.

Стек:

- frontend: React 18, TypeScript, Vite, Tailwind CSS, Framer Motion, Zustand, TanStack Query;
- backend: Express, TypeScript, Prisma, PostgreSQL;
- инфраструктура: Docker Compose;
- тесты: Vitest на frontend и Node test/build на backend.

Тарифы: Free и PRO за 499 ₽ в месяц. Оплата — ручное продление через ЮKassa без скрытых автосписаний. Пока реквизиты магазина не настроены, `BILLING_ENABLED=false`.

## Неприкосновенные продуктовые инварианты

- Автоматический импорт сделок является основным сценарием. Ручной журнал не должен быть центром продукта и может быть только опциональной настройкой.
- Пользователь видит завершённые циклы позиции, а не сырые ордера и частичные исполнения.
- Импорт поддерживает Bybit Spot и Linear USDT/USDC.
- API-ключ Bybit только read-only, без прав на торговлю и вывод средств.
- Повторная синхронизация не создаёт дубликаты и не удаляет пользовательские заметки, теги, эмоции и контекст.
- Неполные или спорные данные получают статус `needs_review`; их нельзя молча включать в подтверждённую статистику.
- Состояния качества данных различаются: `verified`, `needs_review`, `empty`, `syncing`, `failed`.
- Первый запуск различает `connect`, `syncing`, `review`, `failed` и `ready`; только проверенные финальные сделки переводят пользователя в `ready`.
- Метрики для дашборда, аналитики и списков рассчитываются одним серверным источником истины. Не дублируй формулы на клиенте.
- P&L показывается net: с учётом комиссий, funding и доступных корректировок. Не выдумывай точность, если источник не предоставляет необходимые данные.
- Доступ к PRO, глубине истории, количеству источников и частоте синхронизации проверяется на backend, а не только скрывается в интерфейсе.
- Подписка активируется или продлевается только после подтверждённого `payment.succeeded`, повторной проверки платежа через API и идемпотентной обработки webhook.
- Пользователь может удалить источник, сохранённый ключ и импортированные данные.
- Tradeum — аналитический сервис, а не инвестиционная рекомендация. Не обещай доходность.

## Дизайн-направление

Сайт не должен выглядеть как Excel-дневник, набор таблиц или панель из одинаковых линейных графиков. Это продукт для принятия решений и анализа торгового поведения.

- Стиль: премиальный современный монохром с холодным синим акцентом; смысловые зелёный и красный сохраняют своё назначение.
- Поддерживай полноценные светлую и тёмную темы с одинаковой визуальной иерархией, сохранением выбора и применением темы до первого кадра без вспышки.
- Используй единый Inter для текста, контролов и чисел; числам давай tabular alignment без перехода на случайный моноширинный шрифт.
- Фон не должен быть пустым: допускаются тонкая техническая сетка, мягкое свечение, глубина слоёв и сдержанные декоративные элементы.
- Добавляй полезную динамику: понятные hover/focus/pressed/loading состояния, последовательные микроанимации и интерактивные сценарии. Всегда поддерживай `prefers-reduced-motion`.
- Главный дашборд содержит только базовые показатели и следующий полезный вывод. Углублённые данные находятся на профильных страницах.
- Выбирай визуализацию по смыслу данных: heatmap для ритма, распределение для сценариев, radial/bullet для риска, календарь для дисциплины, waterfall для вклада в P&L, scatter для связи риска и результата, cohort/матрицу для повторяемых факторов. Линейный график используй только для настоящего временного ряда.
- Не добавляй график ради красоты. Каждая визуализация должна отвечать на конкретный вопрос и иметь доступное текстовое объяснение.
- Демо-данные на публичных экранах помечай как демонстрационные. В кабинете без источника показывай onboarding/empty state, а не выдуманную статистику.
- Используй настоящие логотипы сервисов только из корректных локальных/официальных источников. Не рисуй поддельные бренды.
- Обязательно проверяй desktop, tablet и mobile, обе темы, клавиатурную навигацию, контраст, переполнение, loading/empty/error/review states.

## Рабочий процесс каждого этапа

1. Восстанови факты: прочитай текущий код, историю Git, схемы, тесты и связанные документы. Не полагайся только на описание задачи.
2. Зафиксируй границы этапа и критерии готовности. Не меняй несвязанный функционал.
3. Для визуального этапа сначала сформулируй цель каждой страницы и каждого блока; затем реализуй цельную систему, а не набор несвязанных карточек.
4. Вноси небольшие логичные изменения, сохраняй существующую архитектуру, если нет доказанной причины её менять.
5. Добавь или обнови тесты для изменённого поведения. Не ослабляй тесты ради зелёного результата.
6. Проверь реальный рендер, интерактивность, консоль браузера и сетевые ошибки. Сборка не заменяет визуальную QA.
7. Исправь найденные проблемы и повтори затронутые проверки.
8. Просмотри итоговый diff на случай секретов, случайных файлов, mojibake, отладочного кода и несвязанных изменений.
9. Передай результат с доказательствами. Не начинай следующий этап автоматически.

Если инструмент или сеть недоступны, отделяй инфраструктурное ограничение от ошибки кода, используй безопасную локальную альтернативу, когда возможно, и точно перечисляй непроверенное.

## Качество реализации

- TypeScript остаётся строгим; не маскируй ошибки через `any`, отключение lint или необоснованные type assertions.
- Не добавляй production-зависимость без необходимости и объяснения.
- Не создавай второй источник истины для метрик, статусов, тарифных прав или платежей.
- Учитывай loading, empty, error, syncing, needs_review и permission/entitlement states.
- Соблюдай доступность: семантическая разметка, label, keyboard, focus, contrast, reduced motion.
- Не переписывай рабочий модуль целиком ради локального изменения.
- Не исправляй несвязанные пользовательские изменения без разрешения.
- Не используй destructive Git-команды (`reset --hard`, принудительный checkout, force push) без прямого запроса пользователя.
- Не изменяй реальные API-ключи и не включай live billing/trading.

## Формат обновлений и финального отчёта

Во время работы сообщай только полезные факты: найденное состояние, принятое решение, результат проверки и текущий прогресс этапа. Не скрывай проблемы и не называй этап завершённым до выполнения критериев.

Финальный отчёт по этапу должен содержать:

- итог одной фразой;
- что изменено и почему это улучшает продукт;
- список изменённых файлов или основных модулей;
- фактические результаты тестов, lint, build и визуальной QA;
- что не удалось проверить и почему;
- риски/ограничения, если они остались;
- текущий статус плана и следующий этап;
- текущую ветку и commit только если commit реально создан;
- запрос подтверждения перед commit/push или переходом к следующему этапу.

Не создавай патч-файл, если работа уже ведётся прямо в актуальном репозитории, если пользователь отдельно не попросил патч.
